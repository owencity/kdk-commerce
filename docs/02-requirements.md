# kdk-commerce 요구사항

사용자 검수 전 초안 · 2026-11-10 범위·예산 갱신. 기준은 [프로젝트 지침](../AGENTS.MD)과 대화에서 합의한 내용이다. [문제정의서](01-problem.md)는 이전 검수본으로, 최근 바뀐 목적과 예산의 반영을 기다리고 있다. †는 검수할 제안이며 확정한 조건이 아니다.

## 1. 무엇을 만들 것인가

고객이 상품을 보고 주문·결제한 뒤 배송을 받고, 필요하면 취소·반품·환불을 요청하는 커머스 시스템을 만든다. 재고보다 많이 팔리지 않는지, 결제 결과를 받지 못했거나 서버가 꺼졌을 때 주문을 어떻게 처리하는지 시험한다. 회사 시스템에 접속하지 않고 직접 만든 상품·주문 데이터와 시험용 외부 API를 사용한다.

전체 흐름은 **상품 조회 → 주문 → 결제 → 출고·배송 → 구매 완료**다. 취소·반품·환불도 다루되, 각 기능을 어느 단계까지 구현할지는 검수하면서 정한다. 구현과 시험은 아직 시작하지 않았다.

| 구분 | 포함할 내용 | 검수 상태 |
| --- | --- | --- |
| 첫 구현 방향 | Kotlin·Spring Boot 모듈러 모놀리스. 상품 조회, 주문, 재고 선점, 모의 결제·ERP·배송, 어드민·CS 화면 | 기능 목록과 세부 조건은 아래 초안을 검수한다. |
| 취소·반품·환불·구매 완료 | 출고와 취소가 겹치는 상황, 주문 일부 반품, 할인·배송비를 고려한 환불, 구매 완료 처리 | F20~F23에서 정책과 구현 단계를 정한다. 전체 흐름에 포함됐다는 이유로 모두 1차 완료 조건으로 확정하지 않는다. |
| AI CS | 카카오톡 문의에 답변 초안을 만들고 상담원이 확인한 뒤 발행한다. 주문·배송 조회와 문서 검색(RAG)을 구분해 평가한다. | 기능 방향은 유지한다. 유료 API 실험 여부·예산은 미정이다. |
| ERP/WMS API | 입고·출고·재고 변경을 전달하는 모의 API | 기존 연동을 유지한다. 줄일지 여부는 별도 결정한다. 실제 ERP 제품 개발은 포함하지 않는다. |
| MSA 전환 | 모놀리스의 부하 한계와 실패를 측정하고 개선안을 검토한 뒤 일부 기능을 분리한다. 같은 조건에서 전후 결과를 비교한다. | 전환 실습은 필수다. 분리할 기능과 비교 기준은 미정이다. |
| 이후 후보 | 자연어 상품 검색, 교환, AI 답변 자동 발행 | 별도 검수 전에는 구현 범위로 확정하지 않는다. |
| AWS 실습 | 프로젝트 진행 중 배포·로그 확인·백업 복원을 실습한다. | 무료 혜택 우선, 월 최대 30,000원. 기본 실행 환경은 노트북이며 AWS 구성은 미정이다. |

전체 쇼핑몰 프론트 UI, ERP/WMS 교체, PG 변경, 처음부터 MSA, Kubernetes·멀티리전, 모델 학습은 현재 범위에 포함하지 않는다. PG는 결제대행사를 뜻하며 처음에는 승인·거절·응답 지연 등을 재현하는 모의 PG를 사용한다.

이미 합의한 처리는 다음과 같다. 재고 선점은 구매 중인 고객에게 수량을 잠시 확보하는 것이다.

- 구매하기에 진입하면 서버에서 재고를 선점한다. 마지막 1개는 한 사람만 확보할 수 있어야 한다.
- 결제 시작 전 취소·만료 또는 PG가 확정한 결제 거절이면 재고를 반환한다.
- 통신 오류로 결제 결과를 모르면 재고 선점과 출고 보류를 유지한다. 결과 확인과 CS 처리를 계속한다. 단순히 시간이 지났다는 이유로 반환하지 않는다.
- 자사몰 재고가 0이면 입고 수량이 자사몰에 반영되기 전까지 품절을 유지한다. 반영된 수량부터 판매한다.

## 2. 필요한 기능과 확인할 결과

F01~F19는 기존 초안의 필수 기능 목록이며 세부 조건은 검수 중이다. F20~F23은 전체 거래 흐름에 맞춰 추가한 검토 항목으로, 정책·구현 단계를 정해야 한다. 고객 행동은 API와 시험용 계정으로 확인한다. 어떤 기능을 묶어 구현할지는 03-domain.md에서 검토한다.

| ID·영역 | 필요한 기능 | 우선순위 | 정상·실패 상황에서 확인할 결과 |
| --- | --- | --- | --- |
| F01 카탈로그 | 고객으로서 판매 중인 상품·가격을 조회하고 싶다. | 필수 | 비판매·미존재 상품을 구분한다. 주문 금액은 서버가 검증하며 고객이 보낸 가격을 그대로 확정하지 않는다. |
| F02 주문 | 고객으로서 주문을 한 번 생성하고 싶다. | 필수 | 동일 사용자·멱등 키·내용의 재요청은 동일 결과, 다른 내용의 키 재사용은 거절한다. 가격 확정 시점은 Q1에서, 멱등 키 보존기간은 Q4에서 정한다. |
| F03 주문 | 고객으로서 내 주문의 진행·실패 상태를 알고 싶다. | 필수 | 타인 주문 조회를 거절한다. 미확정은 결제 결과 확인 중으로 안내하고 주문번호·문의 경로·중복 결제 자제 안내를 제공한다. 실패·취소 완료로 단정하지 않고 확인 후 상태를 갱신한다. |
| F04 판매 가능 재고 | 고객으로서 남은 수량 안에서 구매 권리를 확보하고 싶다. | 필수 | 구매하기 진입 요청을 서버가 처리할 때 선점하고 성공한 경우에만 확보됐음을 알린다. 마지막 재고 1개에 동시 진입해도 선점은 최대 1개다. 확보 실패는 PG 결제 전 알린다. 초과 판매·음수 재고 없이 거절 사유를 기록하고 품절과 재고 확인 불가를 구분한다. |
| F05 판매 가능 재고 | 운영자로서 선점을 확정하거나 해제하고 싶다. | 필수 | 결제 시작 전 취소·만료와 PG가 확정한 승인 거절은 선점을 해제한다. 승인 처리 중·결과 미확정은 일반 만료로 해제하지 않는다. 결제·만료·재처리 순서를 바꿔도 이중 확정·이중 반환이 없다. 예외적인 해제 후 승인 통지는 자동 확정하지 않고 대조한다. |
| F06 판매 가능 재고 | 운영자로서 ERP 원천과 복제본 차이를 확인하고 싶다. | 필수 | 입고·출고·정정 모의 API를 반영하고 중복·역순 갱신과 선점 중 갱신을 시험한다. 타임아웃에 재고를 임의 생성하지 않는다. 재고 0에서 입고된 새 물량은 자사몰 적용 전 품절을 유지하고 적용 후 판매한다. 감소·정정 지연 정책은 Q2에서 별도 검토한다. |
| F07 결제 | 고객으로서 모의 PG 결제를 요청하고 싶다. | 필수 | 주문·금액·선점을 확인하고 PG 승인 요청 전에 결제 처리 중 상태를 기록한다. 같은 결제 의도를 중복 승인하지 않으며 네트워크 오류·타임아웃은 결과 미확정으로 기록한다. |
| F08 결제 | 운영자로서 미확정 결제 결과를 확인하고 싶다. | 필수 | 조회·통지로 PG 결과와 주문을 대조한다. 미확정은 선점·출고 보류를 유지하고 CS 처리 대상으로 연결한다. CS 인계 후에도 결과 확인을 계속한다. 성공 확인 후 주문 확정, 확정 거절이면 반환한다. 미확정 동안 새 결제를 중복 실행하지 않는다. |
| F09 주문·ERP | 운영자로서 확정 주문을 ERP에 전달하고 싶다. | 필수 | 저장 후 전달 전 장애에도 재처리할 기록이 남는다. 동일 주문 재전달이 중복 출고 지시로 이어지지 않도록 모의 수신부와 검증한다. |
| F10 배송 | 고객으로서 출고·송장·배송 상태를 알고 싶다. | 필수 | 모의 배송 상태를 조회한다. 중복·역순 통지로 완료 상태를 이전 상태로 되돌리지 않고 불일치를 기록한다. |
| F11 고객 문의 | CS로서 카카오 문의를 누락·중복 없이 접수하고 싶다. | 필수 | 동일 웹훅은 동일 문의로 식별한다. 접수 응답은 LLM 완료를 기다리지 않으며 작업 전달 실패·재시작을 시험한다. |
| F12 고객 문의 | CS로서 최신 사실과 문서 근거가 있는 초안을 받고 싶다. | 필수 | 주문·배송은 권한 확인한 함수 호출, 정책·승인된 합성 과거 답변은 RAG로 처리한다. 조회·검색 실패 시 사실을 지어내지 않고 검토 사유를 남긴다. |
| F13 고객 문의 | CS로서 초안을 승인·수정·반려하고 싶다. | 필수 | 승인 전 발행은 없고 초안 버전·승인자·판정을 남긴다. 중복 승인·발행 타임아웃·재처리로 중복 답변을 만들지 않는다. |
| F14 AI 운영 | 운영자로서 작은 모델 중심으로 비용을 통제하고 싶다. | 필수 | 모델 라우팅 전후 품질·비용을 비교한다. 모든 유료 호출의 토큰·비용·지연을 집계하고 예산 소진 시 추가 호출을 막아 사람 처리 대상으로 남긴다. 제한 정책은 Q5다. |
| F15 AI 평가 | 검수자로서 RAG와 채점기의 효과를 확인하고 싶다. | 필수 | 유형별 합성 정답을 검수하고 검색 recall@k·답변 품질을 분리 평가한다. 사람 채점 50건과 LLM 채점 일치율, 동일 조건의 RAG 전후 무수정 승인률을 보고한다. 평가 정답을 검색 자료에 섞지 않는다. |
| F16 어드민 | 운영자로서 상품·정책의 최소 설정을 관리하고 싶다. | 필수 | 상품 판매 상태·가격, 버전 있는 합성 정책 자료를 관리한다. 권한 없는 변경은 거절하고 변경 이력을 남긴다. |
| F17 어드민 | 운영자로서 실패·미확정 작업을 확인하고 복구하고 싶다. | 필수 | 주문·결제·ERP 전달·재고 불일치를 조회하고 권한 있는 재조회·취소 요청·재처리를 기록한다. 취소 요청과 PG 취소 완료를 구분하고 버튼 재실행도 멱등성을 지킨다. |
| F18 CS 화면 | CS로서 문의·근거·초안·판정을 한 화면에서 검토하고 싶다. | 필수 | F12·F13의 상태·근거 버전과 연결된 미확정 결제를 확인한다. 담당자·고객 의사·안내·처리 근거를 기록한다. 오래된 초안의 동시 승인은 충돌로 표시한다. |
| F19 CS 알림 | CS로서 결제 확인이 지연되는 주문을 먼저 파악하고 싶다. | 필수 | 미확정 발생 시 담당 목록과 CS 알림을 생성한다. 같은 결제 시도의 재조회마다 새 알림을 만들지 않는다. 알림 전달 실패는 재처리하며 목록은 남긴다. 해결 시 결과를 반영한다. 고객에게 문의를 안내하되 문의 접수를 기다리지 않고 처리 대상을 만든다. |

### 추가로 검수할 기능

다음은 요구사항 제안이다. 정책이 정해지면 입력·기대 결과와 테스트 조건을 보완한다. 표에 적은 것만으로 구현하거나 검증을 마쳤다고 보지 않는다.

| ID | 필요한 기능 | 정할 내용과 확인할 결과 |
| --- | --- | --- |
| F20 주문 취소 | 고객이 주문 취소를 요청하고 처리 결과를 확인한다. | 출고 전후 언제 취소할 수 있는지 정한다. 취소 요청과 출고 처리가 동시에 들어오는 경우를 시험한다. 고객의 요청 접수와 PG의 취소 완료를 구분하고, 응답이 없으면 완료로 표시하지 않는다. 일부 상품만 취소하는 범위도 정한다. |
| F21 반품 | 고객이 받은 상품의 반품을 요청하고 처리 상황을 확인한다. | 반품 가능한 조건, 상품 회수·입고·검수와 환불의 순서를 정한다. 반품 상품을 다시 판매할 수 있는 조건도 정한다. 전체·일부 반품의 구현 단계를 구분하고 중복 요청을 시험한다. |
| F22 환불 | 고객과 운영자가 환불 예정 금액과 실제 처리 결과를 확인한다. | 할인액·배송비·반올림·누적 환불 상한을 정한다. 같은 요청으로 두 번 환불하지 않고, PG 응답이 없으면 결과를 확인할 때까지 환불 완료로 표시하지 않는다. 부분 취소·부분 반품은 선택한 계산 기준으로 시험한다. |
| F23 구매 완료 | 배송 후 구매 완료 여부를 기록한다. | 배송 완료와 구매 완료를 구분하고 누가 언제 확정하는지 정한다. 자동 확정 여부와 취소·반품 처리에 미치는 영향은 아직 정하지 않았다. |

## 3. 성능·복구·비용 기준

새 목표는 †로 제안하고, 결정할 수 없는 숫자는 Q 번호로 연결한다. 해당 값이 미정이면 합격 판정도 보류한다. 실행 환경은 RAM 16GB·CPU 약 4코어 8스레드 노트북이며 실제 가용 자원, 부하 발생기, Cloudflare 경유 여부를 기록한다.

## 6. 열린 질문: 다음에 검토할 내용

사용자는 고객에게 약속할 업무 정책·허용 손실·범위를 결정한다. 작성자는 측정 방법·구현 대안·실험값을 먼저 제안하고 근거를 설명한다. 기술 수치를 사용자에게 처음부터 산정하게 하지 않는다. 아래 예시 숫자는 설명용이며 확정값이 아니다.

`PG 결제 승인`은 결제 성공 처리, `상담원 답변 승인`은 고객에게 보낼 초안의 확인, `PO 확정`은 이 프로젝트의 정책·범위 결정이다. 서로 다른 행위다.

### Q1. 재고 선점·결제 미확정 처리 — 핵심 업무 정책 합의

- 정해진 정책: 구매하기 진입 시 서버에서 재고를 선점한다. 결제 시작 전 취소·만료 또는 PG가 확정한 잔액 부족·카드 정지 등의 승인 거절이면 반환한다. 네트워크 오류로 결과를 모르면 선점을 유지한다. 성공이면 임시 선점을 판매 확정으로 전환하고 판매 가능 수량을 다시 차감하지 않는다.
- 용어: 선점은 구매 중인 고객에게 수량을 임시 확보하는 것이다. 승인 거절은 결제가 성립하지 않은 결과이고, 결제 취소는 이미 승인된 결제를 취소하는 별도 거래다. 네트워크 오류는 둘 중 어느 것도 확정하지 않는다. [근거 1·2·7]
- 제안하는 처리: PG 호출 전에 결제 처리 중으로 전환하고 만료 처리와 충돌하지 않게 한다. 조회·통지로 결과를 확인하고, 재시도가 필요하면 해당 PG·API가 보장하는 범위에서 동일 결제 시도·멱등 키를 사용한다. 화면 닫힘이나 단일 조회의 미존재 응답만으로 실패를 단정하지 않는다. 고객에게 결과 확인 중임을 알린다.
- CS 처리 정책: 결제 결과 미확정은 선점과 출고 보류를 유지하고 CS에 알린다. 원인 미확인 시 고객에게 결제 결과 확인 지연·주문번호·문의 경로를 안내한다. PG 장애가 확인된 경우에만 그 원인을 설명하며 복구 예정 시각을 추정하지 않는다. 고객의 취소 의사는 접수하되 PG 결과 확인 전에는 취소 완료로 표시하지 않는다.
- 대체 결제 제안: 계좌입금 전환은 기존 카드 거래의 실패·취소 등 종결 확인과 고객 동의 후 새 결제 시도로 관리하는 안이다. 기존 미확정 거래를 지우거나 우리몰 상태만 변경해 입금받지 않는다. 취소 요청도 응답 유실 시 결과 확인 대상으로 남긴다. 계좌입금 지원 자체는 별도 범위 검수 전이다.
- 작성자 할 일: 승인·거절 응답 유실, 장기 PG 조회 불가, 선점 만료 경합, CS 알림 유실·중복, 취소 응답 유실·재시작을 재현한다. 중복 결제·재고 반환 없이 고객 요청과 최종 PG 결과가 연결되는지 검증한다. 실제 PG 장애 복구시간은 가정하지 않는다.
- 후속 설계: 핵심 업무 흐름은 합의됐으므로 다시 결정하도록 요구하지 않는다. 예약 만료시간·자동 확인 간격·장기 미해결 대응 주기는 작성자가 근거와 시험안을 먼저 제시한다. CS 채널·담당자, 가격 보장, 취소·환불·대체 결제 범위는 별도 설계 시 검수한다. 미확정 장기화만으로 자동 반환하지 않으며 재고 점유에 따른 판매 기회 손실은 남는다.
- 대안·트레이드오프: 거절 즉시 반환은 다른 고객에게 기회를 주지만 카드 변경 재결제 시 재선점이 필요하다. 짧은 유예는 기존 고객에게 편하지만 그동안 재고를 점유한다. 현재 정책은 즉시 반환이며, 재결제 불편이 커지면 PO 검수로 유예 도입을 재검토한다. 미확정 자동 반환은 점유를 줄이지만 뒤늦은 결제 성공에 대한 취소·보상 위험이 있어 현재 방향에 맞지 않는다.

### Q2. 입고 반영 전 판매 보류와 재고 감소 지연 대응

- 합의: 자사몰 판매 가능 재고가 0이면 ERP 입고가 자사몰에 검증·적용될 때까지 품절을 유지한다. 새 물량 적용 후 판매를 열며, 입고 지연만으로 기존 잔여 물량까지 중단한다는 결정은 아니다.
- 지연의 뜻: ERP 변경부터 자사몰 적용까지의 시간이다. ERP 12:00:00 입고→자사몰 12:00:03 적용이면 3초이며 숫자는 설명용이다. API 수신과 적용도 구분한다. [근거 3]
- 남은 업무 사실: [확인 필요: 같은 재고를 다른 판매처와 공유하는지, 자사몰 몫이 따로 배정되는지]. 실제 계약은 추정하지 않으며 모르면 프로토타입 가정으로 별도 검수한다. 재고의 ERP/WMS 원천과 API 연동은 유지한다.
- 실패 예시: 공유 재고 1개를 다른 판매처가 먼저 확보했는데 감소 통지가 늦으면 자사몰에는 1개가 남아 보인다. 자사몰 안의 동시성 제어만으로 외부 판매처와의 중복 판매까지 막을 수는 없다. ERP 수량을 한 번 조회한 직후에도 다른 판매가 일어날 수 있으므로 최신 조회와 구매 수량 확보를 구분한다.
- 공식 사례: 올리브영은 구매 과정의 재고 API 조회와 자체 저장소를 가진 사용처의 이벤트 구독을 구분한다. 이는 소비 목적별 최신성 요구를 나눈 사례이며, 원문만으로 ERP 예약 API나 우리 선점 정책이 검증됐다고 해석하지 않는다. [근거 8]

| --- | --- | --- |
| 자사몰 판매용 수량 배정 | 다른 판매처가 배정량을 소비하지 않는 약속 아래 자사몰에서 선점한다. 매 구매마다 ERP 응답을 기다리는 의존성을 줄인다. | 판매처 간 물량 재배분이 필요하며 품절·폐기·정정 위험은 남는다. 배정 회수는 진행 중 선점과 충돌하지 않아야 한다. |
| 공통 재고 관리 주체에서 구매 수량 확보 | 모든 판매처가 같은 확보 절차를 거친다. 공유 물량의 중복 확보를 제어할 수 있다. | ERP 또는 별도 공통 주체에 확보·해제·중복 방지 계약이 필요하다. 조회 API만으로 대체할 수 없으며 지연·장애가 구매에 영향을 준다. |
| 마지막 반영 수량으로 판매 | 복제본만으로 구매를 처리해 외부 응답 의존성을 줄인다. | 지연 중 과판매 위험이 남는다. 안전 여유 수량과 지연 감지는 위험을 줄이는 수단이며 0건 보장은 아니다. |

- 추천 초안: 먼저 공유·배정 여부를 확인한다. 배정이 보장되면 첫 안, 공유이고 과판매 0건이 필요하면 두 번째 안의 계약 가능성을 검토한다. 마지막 수량만으로 판매하는 안은 사용자의 불확실한 재고를 신뢰하지 않는 방향에 맞지 않아 우선 추천하지 않는다. 모의 계약을 실제 ERP 기능으로 주장하지 않는다. 재배분 손실·외부 지연·계약 변경을 측정한 뒤 PO 검수로 재검토한다.
- 연동 이상 대응 제안: 누락·적용 실패·정한 지연 한계 초과를 감지하면 영향받는 상품의 새 선점을 보류하고 ‘재고 확인 지연’으로 안내한다. 범위를 특정할 수 없으면 보류 범위를 넓히는 안을 검토한다. 기존 결제 미확정 선점은 Q1대로 유지한다. 원천 대조·누락 반영·선점 정합성 확인 후 재개한다. 이 보류 정책은 검수 전이며 지연 한계는 작성자가 측정안을 제시한다.
- 감지 한계: 마지막 API 응답이 성공했거나 최근이라는 이유만으로 누락이 없다고 단정하지 않는다. 변경 순서·버전·반영 진행 위치 등 모의 계약과 대조 절차를 설계한다. 감지 전 지연 구간의 위험은 위 배정·공통 확보 경계로 다룬다.
- 검증: 외부 판매와 자사몰 마지막 1개 구매의 경합, 감소 통지 지연·누락·중복·역순, 선점 중 정정, 동일 주문의 ERP 반영에 따른 이중 차감, 복구 후 재개를 합성 데이터로 시험한다. 입고 반영 대기로 놓친 판매와 품절 오판을 분리 집계하며 분모는 검수한다. 선택한 계약에서 보장할 범위가 확정되기 전 초과 판매 0건을 달성했다고 쓰지 않는다.

### Q3. 24시간 운영하며 품절을 구매 과정에서 바로 알린다

- 합의한 요구: 노트북은 24시간 운영한다. 자사몰에서 판매 가능 재고 0을 확인하면 품절을 알리고 구매를 막는다. 구매하기 진입 시 서버의 재고 선점 결과로 판단하며, 확보 실패를 PG 결제 단계까지 미루지 않는다. 화면 조회 뒤 다른 고객이 마지막 수량을 선점하는 경우도 검증한다.
- 구분할 것: 24시간 운영 방침은 장애가 전혀 없다는 보장이 아니다. 품절 판단·안내 속도와 서비스 접속 가능 여부는 별도 측정한다. ERP의 미반영 변경까지 자사몰이 즉시 안다고 가정하지 않으며, 재고 확인 불가를 확정 품절로 표시하지 않는다.
- 용어: SLI는 실제 서비스 상태를 측정하는 지표이고 SLO는 그 지표의 목표다. 품절 응답 시간·정상 처리 비율 등을 어떻게 측정할지는 작성자가 먼저 제안한다. ‘바로 안내’의 수치 기준도 측정 결과와 함께 검수하며 사용자가 처음부터 밀리초·백분율을 산정하지 않는다. [근거 4]
- 분모 예시: 주문 시도 1,000건에 재고 100개가 팔리고 900건을 정확히 품절 거절했다면 구매 성사 비율은 10%지만, 900건 모두 시스템 오류는 아니다. 재고 충분 실험의 주문 성공률과 재고 소진 실험의 성공·정상 거절·미확정·오류를 분리 집계하는 안을 제안한다.
- 작성자 할 일: 구매 요청→선점 결과 응답 시간, 품절 표시 갱신 지연, 외부 접속 성공 여부를 각각 측정한다. 실제 상점 UI는 비목표이므로 API·시험용 화면으로 검증 범위를 명시한다. 기존 p99 500ms·99%는 제안값이며 품절 안내나 가용성의 확정 목표로 전용하지 않는다.

### Q4. 복구 실험 결과를 보고 허용 가능한 수준을 결정한다

- 용어: RTO는 장애 후 복구에 허용할 최대 시간, RPO는 복구 가능한 마지막 시점부터 장애까지 허용할 데이터 손실의 시간 범위다. 둘 다 목표이며 실제 복구 시간·손실과 구분한다. 기록 보존기간은 별도다. [근거 5]
- 우선 제안하는 검증: ① 저장장치가 정상인 상태에서 애플리케이션을 종료·재시작하여 접수한 주문·미완료 작업이 사라지거나 중복 처리되지 않는지 확인한다. ② 운영 데이터와 분리된 시험 공간에 백업을 복원하여 마지막 복구 가능 시점·누락된 합성 주문·복구 시간을 확인한다. 두 시험의 데이터 손실 조건을 혼동하지 않는다.
- 복구 완료 판정 초안: 서버 실행만 확인하지 않고 주문 조회, 재고·결제 대조, 미완료 작업 재처리를 확인한다. PG 결과가 계속 미확정이면 안전한 보류·CS 추적이 가능한지 검사하며 결제 완료로 꾸미지 않는다. 모의 PG 승인 후 자사몰 기록 전 종료되는 경우도 포함한다.
- 작성자 할 일: 백업 방식·간격·보존·멱등 키 보존 후보와 비용, 수동 복원과 자동 재시작의 적용 범위를 제시한다. 같은 디스크의 백업만으로 디스크 손상에 대비했다고 주장하지 않는다. 장치 외부 백업의 위치·비용·범위는 제안 후 검수한다.
- 사용자 판단 시점: 지금 RTO·RPO 숫자를 답하지 않아도 된다. 작성자가 ‘어떤 장애에서 몇 분 걸렸고 어떤 기록이 얼마나 빠졌는지, 개선하려면 무엇이 필요한지’를 제시하면 그 결과와 비용을 보고 허용 범위를 판단한다. 탐색 실험 후 목표 후보를 검수하고 별도 검증 시험으로 비교하며, 검증 결과에 맞춰 합격선을 사후 변경하지 않는다. 수치 확정 전에는 복구 성능 합격을 선언하지 않는다.

### Q5. 어떤 AI 오류를 반려하고 어느 품질·비용까지 허용할 것인가

- 뜻: recall@k는 정답 관련 문서 중 검색 결과 상위 k개에 들어온 비율이다. 관련 문서 4개 중 상위 5개 결과에 3개가 들어오면 recall@5는 75%다. 답변 정확도와 별도다. 사람·LLM 채점 일치율도 동일한 채점 기준에서 판정이 같은 비율이다. [근거 6]
- 사용자 판단: 잘못된 배송 상태·근거 없는 정책 답변 등 반드시 반려할 오류는 무엇인가. 직접 작성한 합성 정책·평가 정답과 사람 채점 50건을 검수한다. 초안 60초 목표를 매번 지킬지, 정한 비율 이상 지킬지 검토한다.
- 작성자 할 일: k·평가 규모·품질 기준·모델 선택·요청별 비용 제한의 후보와 평가 방법을 먼저 제안한다. 기존 월 10,000원 예산은 철회됐으며 유료 실험 여부·예산을 정하기 전 호출하지 않는다. AWS 월 30,000원은 별도 실습 예산이다. 1차 전건 상담원 승인은 유지하며 자동 발행 활성화는 별도로 판단한다.

### Q6. 무엇부터 구현하고 어디까지 확인할 것인가

- 사용자 판단: F20~F23의 취소·반품·환불·구매 완료를 어떤 순서와 범위로 구현할지, 모의 ERP/WMS 연동을 유지할지 줄일지 정한다. 기존 구현 1주 목표가 포함하는 작업도 아직 미정이다. 변경 요청→반영 목표 N일은 구현 기간과 다르다.
- 진행 방식: 하루 1시간씩 검토하며 한 번에 문서 하나를 고친다. 매번 합의한 내용·남은 질문·다음 시작점을 기록한다. 검수된 요구사항·설계를 작은 단위로 구현하고 테스트한 뒤 사용자 검수를 받는다. 문서·구현·시험의 완료를 구분한다.
- 작성자 할 일: 범위·작업량과 변경 실험 목록을 제안한다. MSA 분리 트리거는 어느 지표가 얼마 동안 어떤 값을 넘을 때 분리 검토할지 정한 기준이며 보편적인 정답 수치가 아니다. 측정 가능한 기준을 먼저 제안하고 결과를 사용자가 검수한다. 인쇄 3쪽 판정 형식도 작성자가 먼저 제안한다.

미반영 건수·비율, 플랫폼/계약 제약 원인, 실제 프로모션 피크 배수는 계속 미확인으로 유지한다. Q1의 핵심 흐름, Q2의 입고 반영 전 판매 보류, Q3의 24시간 운영·품절 조기 안내는 합의했다. Q2의 감소 지연과 Q4의 복구 기준은 작성자가 구체적인 대안·시험 계획을 먼저 제시한다. Q5·Q6도 예시와 제안을 토대로 순차 검수하며 미정 수치를 지금 일괄 답하도록 요구하지 않는다. 미정 수치와 제안은 확정하지 않는다.

## 7. 이 결정이 가르치는 CS 개념

선점·정정 → 동시성·불변식, 결제 미확정 → 부분 실패·멱등성, 접수·전달·재처리 → 원자성·내구성, 원천·복제본 → 일관성·최신성, 한계 측정 → 자원 경합·대기, AI 평가 → 누출 방지·변수 통제. 업무 규칙의 이유·상태 전이는 03-domain.md, 구현 대안·CS 근거와 실패 검증은 04-design.md로 이어진다.
