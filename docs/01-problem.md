# 자사몰 내재화 문제정의서

검수 전 초안 · 기준: [AGENTS.MD](../AGENTS.MD), 작업 프롬프트 1

## 1. 요약

외부 업체가 결정하는 변경 반영 여부와 작업 시점을 자체 개발로 통제할 수 있는지, 개인 프로토타입의 변경·부하·장애 실험으로 검증한다.

## 2. 현황과 문제

| 유형 | 관찰된 사실 | 검증 지표 |
| --- | --- | --- |
| 소규모 수정 | 문구·설정·배너는 거의 즉시 반영된다. 현재 문제로 보지 않는다. | 참고 기록 |
| 중간 규모 변경 | 기능·흐름 변경은 접수부터 반영까지 약 1주 걸린다. | 접수→반영 일수 |
| 미반영·추가 제약 | 일부 요청은 거절·무기한 보류된다. 기능 추가는 가능하지만 DB 접근이 phpMyAdmin으로 제한되는 등 제약이 많다. | [확인 필요: 미반영 건수/전체 요청 건수·비율, 제약·포기 기능 목록] |

업체 일정에 맞춘 아침 작업으로 프로모션 매출에 약 1시간 영향을 받은 사례가 있다. 손실 금액은 추정하지 않는다. 문제는 변경 속도뿐 아니라 **반영 여부와 작업·장애 대응 시점을 우리가 통제하기 어렵다는 점**이다.

## 3. 목표와 성공 판정

아래는 실험 목표다. †는 프롬프트 1의 제안값으로 PO 검수 전이며, 회사의 관측값이 아니다. 미정 목표가 남으면 최종 성공을 판정하지 않는다.

| 목표 | 값 | 판정 방법 |
| --- | --- | --- |
| 변경 통제 | 리드타임 약 1주 → [확인 필요: 목표 N일], 미반영 0건 | PO와 합의한 변경 목록의 접수·반영 시각, 완료·미완료 사유와 작업 시점 준수 기록 |
| 세일 부하 처리 | 첫 10초 조회 1,000 RPS·주문 100 TPS에서 주문 성공률 ≥99%†, 조회 p99 ≤500ms† | 평시 50 RPS·5 TPS 대비 20배 부하. 70%를 상품 1~3개에 집중시키고 재고 100개가 10초 내 소진되는 시나리오로 측정 |
| 재고 정확성 | 초과 판매 0건, 품절 오판률 ≤1%† | 동시 주문 결과와 합성 재고 원장을 대조. 재고가 있는데 품절로 거절된 비율을 별도 집계 |
| 작업·장애 통제 | 대응·복구 시간 [확인 필요: 목표] | 예정 작업 시간 준수와 장애 주입→탐지→복구 시각 기록 |
| AI 초안·비용 | 접수→초안 ≤1분†, API 월 ≤10,000원 | 유형별 승인률·검색 recall@k·답변 품질·호출 비용·지연 기록. 사람 채점 50건과 LLM 채점 일치율, RAG 전후 승인률 비교 |

주문 성공률은 품절 등 정상 업무 거절과 시스템 오류를 구분하고, 품절 시도 건수도 공개한다. 성공률·품절 오판률의 분모와 AI 품질 합격선은 요구사항에서 PO가 확정한다. 부하 한계까지 실패를 측정한 뒤 일부 기능을 MSA로 분리하고 같은 조건으로 비교한다. 성능 개선은 전제하지 않는다.

## 4. 이해관계자와 충돌 가설

검증할 기대는 운영·MD의 행사 일정 준수, CS의 정확한 초안·승인 부담 감소, 물류·ERP의 재고·주문 정합성, 재무의 비용 상한, 경영진의 매출 영향 감소, 현 업체의 지원 범위·일정 명확화다. 운영의 빠른 변경과 물류의 정합성 검증, CS의 품질과 재무의 비용이 충돌할 수 있다. 실제 요구는 확인 전이다.

## 5. 범위와 제약

Kotlin + Spring 모듈러 모놀리스부터 시작한다. 개인 노트북(RAM 16GB, CPU 약 4코어 8스레드)과 현재 Cloudflare Zero Trust 환경을 쓰며 처리 가능 부하는 측정한다. ERP/WMS가 재고 원천이고 자사몰은 판매 가능 재고 복제본을 가진다. ERP는 모의 API, 카카오는 모의 웹훅으로 연결한다. 회사 코드·실데이터·계약 내용은 사용하지 않는다. AI는 함수 호출과 문서 RAG를 구분하고 비동기 초안을 전건 승인 후 발행한다.

비목표는 ERP/WMS 교체, PG 변경, 처음부터 MSA, Kubernetes, 멀티리전, 자사몰 전체 프론트 UI, 모델 학습·파인튜닝이다. UI는 어드민·CS 승인 화면으로 한정한다. 자연어 상품 검색은 2차 후보이며 자동 발행 활성화는 별도 검수 대상이다.

## 6. 리스크와 대응

- 자체 개발이 운영 부담을 늘릴 수 있다. 작업·복구 기록과 투입 시간을 함께 남긴다.
- 노트북·부하 발생기·네트워크 한계를 애플리케이션 병목으로 오인할 수 있다. 실행 조건과 자원 지표를 기록하고 동일 조건으로 비교한다.
- 구현 속도와 별개로 규칙 검토·검증이 지연되거나 AI 비용·품질이 목표에 못 미칠 수 있다. 최소 기능으로 제한하고 예산 제한·사람 승인을 유지한다. 미완료·미달을 숨기지 않는다.

## 7. 진행 순서와 검토 기준

기존 8주안은 고정 일정으로 사용하지 않는다. 구현은 1주 이내를 목표로 하되 검증된 완료를 뜻하지 않는다. 업무 규칙·설계 검수 → 모놀리스 구현 → 부하·실패 검증 → 분리 대상 검수·MSA 구현 → 전후 비교 순서를 유지한다. 문서 검토·협의와 검증에 시간을 우선 배정하며 전체 기간과 1주 구현 범위는 PO가 확정한다.

업무 논리는 상황·전제 → 가능한 상태 전이 → 지켜야 할 규칙 → 현실의 이유 → CS 근거·대안 → 검증 시나리오·증거로 정리한다. 03-domain.md에서 주문·입고·출고의 사건·예외를 다루고, 04-design.md에서 동시성·영속성·네트워크 실패 및 CPU·메모리·디스크·OS 자원과 연결해 검증한다. 구현 완료와 규칙 검증 완료를 구분한다.
